# Phase 4 전량 출력 전환 — 개발 요청서

> 2026-07-28 · 대상: Phase 4 (CEP 상황 생성) v2.0.0

## 배경

현재 Phase 4는 LLM이 CEP 카드를 만들면서 **3축 점수 판정 → 곱셈 → 정렬 → 상위 N개 선택**까지 한 번에 수행합니다.

문제는 세 축 중 두 축을 LLM이 판정할 근거가 입력에 없다는 것입니다.

| 축 | 판정 근거 | Phase 4 입력에 존재 |
|---|---|---|
| 시장성 (market_potential) | 후보와 연결된 검색어의 검색량 | ✗ |
| 브랜드 적합성 (brand_fit) | 자사 브랜드·제품 자산 정보 | ✗ |
| 입증 가능성 (provability) | 인용 근거의 강도 | ✓ |

두 축이 항상 `score:3, estimated:true`로 고정되므로 실질적으로 `3 × 3 × provability` — **입증 가능성 한 축의 정렬**입니다. 여기에 LLM의 산술·정렬 오류가 얹혀 노이즈만 늘어납니다.

또한 상위 N개 절단은 검색량이 작은 잠재 CEP를 프롬프트 단계에서 유실시킵니다.

## 요청 요약

**판정은 LLM, 계산과 선별은 백엔드로 분리합니다.**

- Phase 4: 장면 번역 + 진입점 자격 판정 + `provability` 판정 → **근거가 허용하는 만큼 후보 전량 출력**
- 백엔드: 검색량으로 `market_potential` 산출 → `brand_fit` 확보 → `cep_score` 계산 → 정렬·선별

---

## 1. 파서 — 출력 계약 변경 수용

**필드명은 전부 불변입니다.** 값의 생산 주체와 배열 길이만 바뀝니다.

| 항목 | AS-IS | TO-BE |
|---|---|---|
| 최상위 배열 길이 | `requested_count` 정확히 일치 | **가변** (0 ~ 상한) |
| `evaluation.market_potential` | LLM `{score, estimated}` | **`null`** → 백엔드가 채움 |
| `evaluation.brand_fit` | LLM `{score, estimated}` | **`null`** → 백엔드/사용자가 채움 |
| `evaluation.provability` | LLM `{score}` | 변경 없음 (LLM 유지) |
| `cep_score` | LLM 곱셈 결과 | **`null`** → 백엔드 계산 |
| `situation` `context` `w7` `kbf_hints` `rtb` `source_ref` `evidence_unit_ids` | — | 변경 없음 |

**개발 항목**

- 배열 길이 검증(= requested_count) 제거
- `evaluation` 하위 두 축과 `cep_score`의 `null` 허용
- 카드 저장 시 `cep_score = null` 상태를 "미계산"으로 구분 (0과 구별되어야 함)

## 2. 시장성 자동 산출 (검색량 연동)

책의 정의: *"CEP 후보와 직접적으로 연결된 검색어들의 검색량을 바탕으로 시장의 크기를 정한다."*

**처리 흐름**

```
카드(situation/context) → 대표 검색어 추출 → 검색량 조회 → 합산 → 1~5 스케일링
```

**결정이 필요한 지점**

- **검색어 매핑 방식** — (a) 카드 텍스트에서 키워드 추출 후 조회 (b) Phase 3 단계에서 수집한 쿼리를 카드에 연결해 전달. (b)가 정확하지만 Phase 3 출력 구조 변경이 필요합니다.
- **1~5 스케일 기준** — **카테고리 내 분위수 방식을 권장합니다.** 절대 임계값(예: 월 1만 회 이상 = 5점)은 카테고리마다 볼륨 스케일이 달라 프로젝트 간 비교가 불가능해집니다.
- **조회 실패 시 처리** — `null` 유지 vs 중립값 3

## 3. 브랜드 적합성 확보 경로

자동 산출 근거가 없습니다. 세 가지 안 중 선택이 필요합니다.

| 안 | 내용 | 비용 |
|---|---|---|
| A | 프로젝트 단위 기본값 3 고정 | 낮음 |
| B | 카드별 수동 입력 UI (기본 3, 사용자 조정) | 중간 |
| C | Phase 1/2 브랜드 자산과 대조하는 별도 LLM 호출 | 높음 |

**A로 시작해 B를 추가하는 순서를 권장합니다.** C는 브랜드 자산 데이터가 구조화된 뒤에 검토.

## 4. cep_score 계산·정렬

- `cep_score = market_potential × brand_fit × provability` (각 1~5, 정수 곱)
- 세 축 중 미확정이 있을 때의 표시 정책 필요 — 예: 잠정 점수로 표기하거나 정렬에서 후순위 처리

## 5. UI — 카드 수 가변 대응

- 카드 수가 프로젝트마다 달라지므로 목록에 **정렬(cep_score / provability)과 필터** 필요
- 최종 선별 기능 — 운영 기준상 핵심 5~7개 CEP를 마킹해 하류 Phase로 넘기는 흐름
- 미계산 상태(`cep_score = null`) 카드의 표시 방식

## 6. 마이그레이션·회귀

- 기존 프로젝트의 `cep_score`는 LLM 산출값입니다. 재계산 여부 결정 필요 (혼재 시 프로젝트 간 비교 불가)
- 회귀 검증: 동일 프로젝트 재생성 후 ① 카드 수 변화 ② provability 분포 ③ 기존 상위 N과의 겹침률

---

## 제품 판단이 필요한 미결정 사항

1. `requested_count`를 제거할지, **상한(max)** 으로 의미를 바꿔 남길지
2. 카드 수 상한을 둘지 (근거가 많은 카테고리에서 과다 생성 가능)
3. 2번 검색어 매핑을 (a)로 갈지 (b)로 갈지 — (b)면 Phase 3 출력 변경이 함께 필요

## 단계 분할 제안

| 단계 | 범위 | 선행 조건 |
|---|---|---|
| 1차 | §1 파서 계약 변경 + `brand_fit` 기본값 3 + `cep_score` 백엔드 계산 | 없음 |
| 2차 | §2 검색량 연동 | 검색어 매핑 방식 확정 |
| 3차 | §3-B 수동 입력 UI + §5 선별 UI | 1차 완료 |

1차만으로도 LLM의 산술·정렬 오류가 제거되고 잠재 CEP 유실이 멈춥니다.
