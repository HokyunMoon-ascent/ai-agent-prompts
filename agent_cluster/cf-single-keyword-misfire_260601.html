왜 이중 분석으로 폭주하고, 없는 키워드 B를 지어내는가

agent_cluster 프롬프트(v.0.6.3) — 단일 입력 오작동 근본 원인 진단

진짜 원인은 데이터가 아니라 프롬프트다. "A/B"가 두 가지 뜻으로 충돌하면서, 모델이 클러스터 ID "B"를 두 번째 입력 키워드로 오인했다.

1데이터로 확정한 사실

입력은 명백한 단일 키워드였다

문제 JSON의 입력 라인과 CSV를 직접 파싱한 결과 — 텍스트 신호와 데이터 신호 둘 다 "단일"을 가리킨다. 그런데도 모델은 6섹션 이중 분석을 냈다.

EVIDENCE 01

src 컬럼은
전부 A 하나뿐

2,180 / 2,180행 = A

CSV src 컬럼 고유값은 A 단 하나. 데이터상으로도 소스 키워드는 1개다. (입력 라인도 Total source keywords: 1, A=버티컬 마우스)

EVIDENCE 02

클러스터 ID는
A부터 Q까지 17개

A~Q 17개 클러스터

c(클러스터) 컬럼에는 B·K·L·Q 등이 가득하다. 모델은 이 클러스터 "B"를 입력 키워드 "B"로 착각할 구조적 빌미를 얻는다.

EVIDENCE 03

"인체공학 키보드"는
데이터에 없다

0 행 (가공)

모델이 키워드 B 시장으로 제시한 인체공학 키보드(7,906) 노드는 CSV에 존재하지 않는다. 있는 건 인체공학 책상·마우스패드뿐 — 명백한 날조.

2결정적 원인

"A/B"가 두 가지 뜻으로 충돌한다

프롬프트 안에서 알파벳 라벨이 서로 다른 두 축에 동시에 쓰인다. 단일 키워드 입력에서는 이 둘이 정면 충돌한다.

① 소스 키워드 라벨

Source keywords: A=버티컬 마우스
(이중일 때만) B=<키워드2>

입력 키워드가 1개인지 2개인지를 가리키는 라벨. 지금은 A 하나뿐.

⇄

② 클러스터 ID (c 컬럼)

클러스터 매핑: 0→A, 1→B, 2→C … Q
데이터: 클러스터 B = 25행 실재

군집 식별자. 데이터에 B가 멀쩡히 있으니, 모델은 "키워드 B도 있다"고 오판한다.

그래서 무슨 일이 벌어졌나. 모델은 클러스터 "B/K/L/Q"의 존재를 "두 번째 입력 키워드 B"의 증거로 받아들였고, 키보드 관련 클러스터(Q)를 가공의 키워드 B = 인체공학 키보드에 끼워 맞춰 6섹션 이중 분석으로 폭주했다. 사용자에게 "src에 A~Q가 있다"고 답한 것도 클러스터 c 컬럼을 src로 착각한 동일한 혼동이다.
3기대 vs 실제

4섹션이어야 할 답이 6섹션으로

프롬프트 규칙상 단일 입력은 4개 섹션만 출력해야 한다. 실제 출력은 교차영역·개별시장까지 붙은 6섹션이었다.

기대 (단일 = 4섹션)

4
분석 개요 · 검색목적 클러스터 · From→To 흐름 · 인사이트.
키워드 B 언급 없음, 교차영역 없음이 정상.

실제 (오작동 = 6섹션)

6
위 4개 + 교차영역 분석 + 개별 시장·타겟 분석.
"통합 시장", "두 키워드 동시 조회" 같은 이중 전용 서술이 전면 등장.
4원인 분해

세 겹으로 쌓인 원인

충돌(①)이 방아쇠라면, 약한 판별 신호(②)와 이중 프레임 템플릿(③)이 오작동을 증폭·고착시켰다.

원인 1 · 결정적

A/B 라벨 충돌

방아쇠
  • 소스 라벨(A/B)과 클러스터 ID(A~Q)가 같은 알파벳
  • 클러스터 B 존재 → 키워드 B 존재로 오인
  • 가공 키워드 B 생성의 직접 원인
원인 2 · 증폭

판별 신호가 약함

데이터 근거 미사용
  • 단일/이중 판단이 텍스트 토큰 1개에만 의존
  • 가장 확실한 src 컬럼은 미문서화·미사용 (전체 프롬프트 등장 1회)
  • 거대 키워드 반복 덤프로 lost-in-the-middle 가중
원인 3 · 고착

템플릿이 이중 전제

출력 형식이 유도
  • 섹션2 "성격: 키워드A 중심 | 키워드B 중심"
  • 섹션5·6 전체가 "키워드 A / 키워드 B" 전제
  • 단일 모드 하드 게이트·B생성 금지·자가검증 부재

같은 단일 입력에 대해, 현재는 날조된 B 시장이 포함된 6섹션이 나온다. 기대값은 B가 일절 없는 4섹션이다.

6왜 이렇게 됐나

예상 질문에 답하기

데이터가 잘못 들어온 건 아닌가?

아니다. 입력 라인 Total source keywords: 1, src 전부 A — 데이터는 일관되게 단일이다. 문제는 데이터를 읽는 프롬프트의 라벨 충돌이다.

모델이 규칙을 안 읽은 건가?

규칙은 있다("1이면 4섹션"). 하지만 판단을 버려진 텍스트 토큰 1개에만 맡겼고, 데이터에 실재하는 클러스터 B가 그 토큰을 이겨버렸다.

왜 하필 "인체공학 키보드"인가?

키보드 관련 클러스터(Q 등)가 데이터에 있으니, 모델이 "키워드 B는 키보드일 것"이라 추론해 그럴듯한 이름을 창작했다. 검색량 7,906도 인접 노드에서 끌어온 값이다.

"데이터에 없는 것 지어내지 마라" 규칙이 있는데?

있다. 그러나 그 규칙은 수치 인용에 걸려 있고, 키워드 개수 판별에는 강제 게이트가 없다. 그래서 B 생성을 막지 못했다.

7진단 검증

이 진단이 맞는지 이렇게 확인한다

  1. 1
    src 고유값 재확인문제 JSON CSV에서 src 컬럼 distinct = {A} 단일임을 재파싱. 이중이라면 A·B 둘 다 나와야 하는데 그렇지 않음.
  2. 2
    날조 키워드 부재 확인n(키워드명) 컬럼 전체에서 "인체공학 키보드" 완전일치 검색 → 0건. 모델 출력의 키워드 B 시장이 데이터 무근거임을 입증.
  3. 3
    충돌 가설 재현 테스트동일 단일 입력 + 클러스터 라벨을 숫자(0,1,2…)로 바꾼 변형 데이터로 재실행. B 오인이 사라지면 A/B 충돌이 방아쇠임이 확정.
  4. 4
    판별 신호 보강 A/B 테스트"입력 키워드 수 = src 고유값 개수"를 명시한 프롬프트와 현행을 비교. 전자에서 단일 입력이 4섹션으로 안정되는지 관측.
8한 문장 요약
단일 키워드인데 이중으로 답하는 건 데이터 오류가 아니라 "A/B" 라벨 충돌 때문이다.
가장 확실한 신호인 src 컬럼을 판별 기준으로 쓰고, 클러스터 ID와 소스 라벨을 분리하면 풀린다.
